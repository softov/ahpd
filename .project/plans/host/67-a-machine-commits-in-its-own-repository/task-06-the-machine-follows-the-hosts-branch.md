## Objective

Before a turn starts, and after a changeset operation, a machine whose branch holds nothing the host has not fetched is set to the host's checked-out branch and commit, its index reset to it; a machine holding unfetched work is left as it is.

## Files

- `UPDATE: packages/sdk/src/types/computers.ts` - `follow?(id: string): Promise<void>`.
- `UPDATE: packages/computer/src/runtime.ts` - `follow`: read the host's `HEAD` and branch; in the machine, where its tip is the host's last fetched commit or an ancestor of the host's tip, `update-ref`, `symbolic-ref HEAD` for a branch the host switched to, and `reset -q`.
- `UPDATE: packages/sdk/src/host/spawn.ts` and `changesets.ts` - call `follow` on `chat/turnStarted` and after an operation.
- `UPDATE: packages/computer/test/computer-git-fetch.test.ts` - the cases below.

## Steps

1. Failing case first, real Docker: a commit made on the host between turns is not the machine's `HEAD` at the next turn.
2. `follow` reads the host with the hardened argv and writes only in the machine.
3. The objects need no copy: the alternates reach the host's.

## Validation

- `computer-git-fetch.test.ts`: a host commit is the machine's `HEAD` after `follow`; a host `checkout` of another branch moves the machine to it; a machine with an unfetched commit is left and the log says so.
- sdk test: `follow` on `turnStarted` and after `commit`.
- `npx vitest run packages/computer packages/sdk/test` passes.

## Resume

- **Implemented** 2026-10-06 on `build/agents/c016a0e4`.
- `packages/computer/src/runtime.ts` gains `follow(id)` on `ComputerRuntime` and the module-internal `followOfMachine`. It reads the host in the tree with the hardened argv every git here runs (`hostGit`, so `gitArgv`): the branch by `symbolic-ref -q --short HEAD`, empty where the host is detached, and the commit by `rev-parse --verify --quiet HEAD`, and it returns at once where the tree has no commit to hand over (the same guard `bringBackOfMachine` has). It asks the machine the same two questions through `argvInto`, which is both roads - a dev container is reached the way every other command in it is - and where the machine has no commit of its own it answers nothing. It steps aside where the guard is not `fetch`: such a machine has no git directory of its own, so it already answers from the host's.
- The hand-over is skipped where both halves already match - the machine on the host's branch at the host's commit - so a turn of a machine nothing happened to writes nothing and above all does not touch an index an agent is working in. Where the commit differs there are two checks, each a log line and a return: `git cat-file -e <tip>^{commit}` in the host's tree, which fails for work the host has never fetched, and `git merge-base --is-ancestor <mine> <tip>`, which fails for a branch that does not lead on from the machine's commit - a person's rebase, reset or their own commit. The two are distinguished on purpose: the first says `it is at <sha>, which the host has not fetched`, the second `<branch> does not lead on from <sha>`, because the host holding the commit and the branch not leading on from it are different things a person does about.
- The writes are in the machine and nowhere else: `update-ref refs/heads/<branch> <tip>` (which makes the branch where the machine does not have it, so a host `checkout` of another branch moves the machine onto it and leaves the branch the machine was on exactly where it was), `symbolic-ref HEAD refs/heads/<branch>`, and `reset -q`; for a host on no branch `update-ref --no-deref HEAD <tip>` and the same `reset`, so a detached host leaves the machine detached. `reset` is not `--hard`: the folder is the host's own working tree and holds what the agent left there, and the reset only says which commit that is. Nothing is copied: a commit the host made is an object the machine already reads through the alternates.
- `packages/sdk/src/types/computers.ts`: `ComputerPort.follow?(id)` with the decision named, `undefined`-shaped for a machine that is not there and absent on a port whose machines commit in the host's own git directory. `packages/computer/src/plugin.ts` hands the runtime's own call on as `made.follow(id)`, as it does for `bringBack`.
- `packages/sdk/src/host/machines.ts` gains `followOf(uri)`: the same shape as `bringBackOf` and for the same reason - the name through `ctx.heldAs`, nothing asked for a session in no machine, and a port that throws is the log line `computers: setting <id> to the host's branch for <uri> failed: <message>` rather than a turn that does not start. What a machine that could not be moved costs is one turn on a branch that is behind, which is what it was before this existed; refusing the turn would cost the work. `Machines` carries it and `packages/sdk/src/host.ts` hands it to the context.
- The turn-start moment is `packages/sdk/src/host/lifecycle.ts`'s `beginOrRun` and not `spawn.ts` as this task's *Files* names: `spawn.ts`'s hook fires on the backend's own `chat/turnStarted`, which is after the turn has begun, and `beginOrRun` is the single road every turn takes - a live session, one resumed from disk, a chat's first message, a message queued behind a running turn. `run()` is what it was; `turn()` wraps it, so the follow is awaited before `session.begin` or `session.ran`. The doc's "a promise only for a turn that had to be asked about" gains "or one in a machine": a session in no machine is still begun in the tick the turn arrived in, which is every turn of a session on this host.
- A message queued behind a running turn is deliberately not handed the branch. The turn it becomes is run by the backend's own queue, with no host-side moment left to follow at, and a hand-over writes the machine's own ref and index - not something to do to a machine an agent is in the middle of a turn in, where a `reset -q` would drop an agent's staged work. Nothing is lost by it: the fetch at the running turn's end puts the machine's own commit on the host's branch, so the two are in step without it.
- The operation moment is `packages/sdk/src/host/resourcemethods.ts`'s `invokeChangesetOperation` and not `changesets.ts` as the *Files* names - the same departure task 05 recorded, since that is where a changeset's verbs are actually invoked and `changesets.ts` has no access to the port at all. `followOf(at.owner)` runs after `contentMoved`, so the host's own bookkeeping is done first and the machine is handed what the operation left. A rejection is `askedOf`'s log line and the operation is already done.
- A regression this task surfaced and fixed: `packages/sdk/src/host/lifecycle.ts`'s `beginTurn`. A turn that waits on a policy check or on a machine now begins inside a promise, so a backend that throws while it is begun - `session-fixed-key.test.ts`'s `refuses a waiting turn the backend throws on, to the client that sent it` - became an unhandled rejection and a client waiting for an answer that never came, where a synchronous throw had reached the dispatch's own `catch` and been refused. `beginTurn` now takes a rejection as a refusal in the error's own words; the case passes again, and no other case in either package moved.

- **Review round** 2026-10-06: in `follow`, a branch of the machine's is now re-pointed only where the commit it is being pointed at leads on from it. The machine's `HEAD` already had that check; the branch of the host's name the hand-over moves it onto did not, and both writes that move it - `checkout -q -B <branch> <mine>` in `followOfCopy` and `update-ref refs/heads/<branch> <tip>` in `followOfMachine` - would drop a commit such a branch held that the machine's `HEAD` was not on top of, which is the only copy of an agent's work. `movesOver(inMachine, branch, tip)` is that check, asked in the machine because the branch is the machine's own, and true where the machine has no branch of that name or is already at the commit named; where it is false the machine is left exactly where it is and the log names the branch that holds work it is not on top of. The doc comment above `followOfMachine` says so as well: what the machine is at, and the branch of that name it is about to re-point.
