## Objective

A machine with no `ahpd.git` label whose mounts hold a writable bind inside its session's git directory is never adopted or entered: ahpd removes it, the session is told `<machine> was made with the host's git directory writable, so it was removed; the next turn makes a new one`, and the next start makes a `fetch` machine.

## Files

- `UPDATE: packages/computer/src/runtime.ts` - `madeUnderBind(record)`: no `ahpd.git` label and a `Mounts` entry with `RW: true` whose source is the git directory or inside it.
- `UPDATE: packages/computer/src/plugin.ts` - adoption at startup and entering a session skip such a machine and remove it, with the sentence above in the log and to the session.
- `UPDATE: packages/computer/test/computer-disposable.test.ts` - scripted Docker records with and without the label.

## Steps

1. Failing case first: a scripted record with a writable `<gitDir>/logs` bind and no label is adopted today.
2. Detect, remove, tell; no `bringBack`, since its commits are already in the host's repository.
3. Planted links are what task 02's refusal catches on the next start.

## Validation

- `computer-disposable.test.ts`: the old machine is removed and not entered; a labelled `fetch` machine and an `open` machine are entered as before; the next start makes a `fetch` machine; a link left under `logs/` refuses it naming the link.
- `npx vitest run packages/computer` passes.

## Resume

- **Implemented** 2026-10-06 on `build/agents/c016a0e4`.
- `packages/computer/src/runtime.ts` gains `madeUnderBind(record)`, exported beside `hostOf` and `disposableOf`: a machine whose labels hold no `ahpd.git` whose mounts hold a read-only bind of a path in a git directory. Two helpers are new with it - `mountsOf(record)`, one machine's `Mounts` array as its own record says it, and `inGitDirectory(source)`, which reads the directory itself or anything in it from the path alone (`/(^|\/)\.git(\/|$)/`), since nothing else in a record says where a session's git directory was.
- **This departs from this task's *Files* line and from the plan's row, both of which say a writable bind.** A `RW: true` test cannot tell the two old guards apart, and removing on it breaks a bullet of this task's own *Validation*: the old `open` guard mounted the git directory itself writable and nothing else, so "a writable bind inside the git directory" is every old `open` machine - which is exactly the machine *Validation* says is entered as before. It also misses the main-checkout case of the old allowlist, whose only writable bind is the tree the git directory sits in and whose writable git paths are reached by binding them over a read-only git directory. The read-only bind of a git path is the invariant of both: the p7 denylist mounted the git directory read-only with `hooks/`, `config`, `worktrees/`, `modules/` and the session entry's `config.worktree`/`commondir`/`gitdir` read-only over it, the p2 allowlist mounted the git directory itself read-only plus pins on a main checkout, and `open` has no read-only binds at all - the superseded decision's own line, "`gitGuard: "open"` is unchanged: no read-only binds", and `git show 56d881c^:packages/computer/src/gitdir.ts`, lines 90-180, are where that is read from. The plan's rule and this task's *Validation* therefore cannot both hold literally, and the *Validation* is the one kept; a later plan written against this one should spell the rule as the read-only bind.
- A fetch machine is excluded by its label first, and has to be: under `fetch` the host's `<gitDir>/objects` is mounted read-only at `/opt/ahpd/host-objects`, which is a read-only bind of a git path on every machine this plan makes. The label is what every machine made since carries, so a machine without one is one made before - and one whose mounts hold no read-only git path is an old `open` machine, which is kept and entered as before.
- `packages/computer/src/plugin.ts` gains `underBindSaid(id)` - the sentence, `computer://<id> was made with the host's git directory writable, so it was removed; the next turn makes a new one`, spelled in the `computer://<id>` shape every other sentence about a machine uses - and `dropUnderBind(record, id)`, which removes the machine through `made.remove` and answers whether it went. No `bringBack` is asked of it, as this task's steps say: its commits are already in the host's repository, since it wrote there. `made.remove` itself still asks the runtime's own `bringBackOfMachine`, which steps aside for any machine whose label is not `fetch`, so nothing is run in the machine before it goes and no volume is removed with it.
- Two roads meet such a machine, and they differ in who can hear them. The startup listing, at the top of its loop, reads each listed row's record and drops it before anything is adopted or entered - the log is where a daemon says what it did to a machine nobody was watching. A session asking for one goes through the port's `how`, which removes it and throws the sentence: that is the only road in the plugin that reaches a session, since `PluginContext` has no channel to one and the port's `enter` is a call the host makes inside a promise whose throw `inMachine` swallows into `ctx.log` - so `enter` is left alone, and a machine the listing never saw is refused where the session can read it. What the session gets is the plan's sentence and not `There is no computer called <id>`, which would also be true and would not say why.
- Another daemon's machine is left where it is, with one line saying so, and `how` refuses it in a variant of the sentence that names whose it is: a daemon neither enters another's machine nor removes it, the rule every disposable machine already follows - decision `a-daemon-adopts-only-the-disposable-machines-whose-session-it-keeps`. The daemon label is absent on the oldest machines, and a machine nobody claimed is nobody's and goes.
- "The next turn makes a new one" holds where the session's setting names a source: the client sends `disposable:<profile>` again and `placedIn` makes a machine with this daemon's guard. Where the stored config holds the removed `computer://<id>` instead - the shape a daemon that restarts keeps - `placedIn` returns early and the next start answers `There is no computer called <id>`, since the machine is gone and no daemon remembers which road removed it. A person picks a machine or a source then; the log line from the removal is what says which machine went and why.
- A listing row carries no mounts, so the startup loop reads each machine's record with `made.inspect` rather than the row. That is one or two extra `docker` calls per listed machine at startup, and it is the price of leaving `Machine` - the shared listing type - alone; a `git` or `mounts` field on it would have saved them, and would have been an SDK change this task's *Files* do not name.
- `packages/computer/test/fixtures/docker.mjs` gains `RW` on the mounts `recordOf` renders, read from the short form's third `:ro` - without it a scripted machine's record could not say which of its binds are writable, and the fixture would be answering a question `docker inspect` answers.
- `packages/computer/test/computer-disposable.test.ts` gains three cases under a *Task 07* heading, all run red first against a `madeUnderBind` that answered `false` (the machine left standing, the sentence never said, `how` resolving a descriptor instead of refusing): the machine a daemon before this one left up is removed at startup in one sentence and the session's next start makes a `fetch` machine, with no `left behind` line, no bundle and no volume removal; a labelled `fetch` machine and an old `open` machine - whose mounts are a writable git directory and nothing else - are left alone and still reached, while the old allowlist's machine beside them goes, which is the read-only bind doing the separating; and a machine the listing never saw is refused by `how` in the sentence and removed as it refuses.
- This task's last *Validation* bullet is task 02's case, already in the same file: `refuses a data directory of the git directory that is a link, which git never makes` plants a link at `<gitDir>/logs` and shows the next start refused naming it - which is what catches what an old machine wrote into the host's git directory.
