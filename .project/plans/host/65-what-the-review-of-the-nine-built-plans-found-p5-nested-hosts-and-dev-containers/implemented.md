A nested session that restarts has one inner host at a time and keeps the conversation it had, and a resume the inner host cannot serve is a session made there rather than a sentence. A worker chat that will not open is a log line instead of an unhandled rejection that would end the daemon, a close during a create disposes what was made, and deleting a nested session that is not running deletes the machine's copy too, as the profile's `nestedDelete` says. `computers.json` that could not be read is never written over. On a host with a users directory no dev container is made at all until `devcontainer.folders` names the folders, and every route refuses with the one sentence naming the option. A computer is found by the name this host gave it: a container, image or volume that merely shares its name is never handed to `stop`, `restart`, `exec` or `rm -f`.

## What was built

- [`code://packages/sdk/src/nested.ts`](../../../../packages/sdk/src/nested.ts) - a `gone` promise on the session, resolved by the same two events that set `exited`, and `close` memoised in `closing` so a second caller waits on the first caller's sequence; `removing` decides whether the inner session is disposed, so a restart keeps the transcript the new host resumes and a removal disposes it. `make` keeps its create in `making`, which `close` reads, so a create in flight is awaited and disposed rather than abandoned. The resume path calls `createSession` too when the inner host answers `-32001`, with any other refusal raised as it came and a line logged. `deleteNested` starts the machine's host, lists its sessions and disposes the one whose resource is the recorded inner id, bounded by `DISPOSE_WAIT`, a machine that is not there being a log line rather than a throw. `openWorker`'s tail - the `subagent` seam, the parts written into the opened chat, the subscription that follows - sits in a `try` that logs `the worker chat <inner> could not be opened: <reason>`, with the subscribe's own catch left outside it.
- [`code://packages/sdk/src/host/lifecycle.ts`](../../../../packages/sdk/src/host/lifecycle.ts) - `restart` collects `chat.close(false)` into `stopping` and awaits it as the last thing before `spawn`, after the machine and worktree juggling; `removeSession`'s not-held branch calls `deletedInside` before the backend's delete.
- [`code://packages/sdk/src/types/session.ts`](../../../../packages/sdk/src/types/session.ts), [`code://packages/sdk/src/types/plugin.ts`](../../../../packages/sdk/src/types/plugin.ts) - `Session.close(removing?)`, which a backend declaring `close(): void` still satisfies; `PluginContext.hasUsers`, absent meaning nobody signs in here.
- [`code://packages/computer/src/owners.ts`](../../../../packages/computer/src/owners.ts) - `read` answers `undefined` for a file that is there and could not be read, parsed, or has something other than an object at the top, and `{}` for one that is not there. The five writers go through `writable`, which logs `not writing <path>: it is there and could not be read, so the records it holds would go with the write` and answers nothing, each caller returning on it.
- [`code://packages/computer/src/plugin.ts`](../../../../packages/computer/src/plugin.ts) - `folderFor` refuses every folder on a host whose plugin context has `hasUsers`, with `This host has a users directory, so no dev container is made from <folder> until its operator names the folders it may use in devcontainer.folders`; the one check covers the create body, `devcontainer://<setting>`, the picker's row and the relay's `connect`. `nestedDelete: 'inside' | 'record'` is a profile key read beside `secretUnreadable` and refused by name at load when it is neither.
- [`code://packages/computer/src/runtime.ts`](../../../../packages/computer/src/runtime.ts) - `containerOf` reads the record `docker inspect <id>` answers and takes the id only when that record is this host's or adopted; otherwise it asks the `ahpd.name` label the create wrote. A name that answers to something this host did not make is `undefined` - what `inspect` already answers for a name Docker does not have - and `containerOrFail`, the same lookup for `stop`, `start`, `restart`, `remove` and `exec`, refuses naming the id.
- [`code://docs/COMPUTER.md`](../../../../docs/COMPUTER.md) - the `devcontainer.folders` allowlist, resolved paths, and that the list is required on a host that has a users directory, with the decision linked.
- [`code://packages/server/src/plugins.ts`](../../../../packages/server/src/plugins.ts) - `loadPlugins` answers `users: true` for a plugin when the base it folds in carries a users port, and `loadOne` reads `hasUsers` from it, so a plugin cannot be told one thing about the host and handed another. `run.ts` needs no flag set for it.

## Review fixes

- A restart could wait for ever on the host it had stopped. `gone` resolved on the process's `close` and on an `error`, and `close` is emitted only once the child's pipes have closed - so a machine whose host leaves something behind holding its stdout (a daemon it started, a shell's background job) is gone with `close` still to come, and `await gone` in `close(false)` waited for that something instead. `opened.on('exit', ...)` resolves `gone` too, and the await is bounded by `KILL_AFTER` plus a margin, `HANDOVER_WAIT`: after it, the restart is logged as going on without the old host, because a process that has been `SIGKILL`ed and has not gone a second later is not writing the transcript the new one takes over. The two waits the review named are bounded by that one: `lifecycle.ts`'s `Promise.all(stopping)` awaits these same `close(false)` promises, so there is nothing there to bound a second time. The case in `nested-process.test.ts` is `a restart goes on once the process is gone, with its pipes still held open` - a real `sh -c 'sleep 8 & exit 0'`, whose `sleep` holds the pipes - and it read `still open` after six seconds before the fix. `nested-proxy.test.ts`'s `a restart goes on when the host inside it stopped will not go` is the bound itself, over a process that takes `SIGTERM` and stays: it read `still open` before, and now the close settles after `HANDOVER_WAIT` with one line saying so.
- A `close` that arrived while the host inside was still being started returned at once, because `host` is set only when `startInside` answers - so a restart started the new host while the old one was still coming up. `bringUp()`'s promise is kept in `starting`, and a restart whose `host` is undefined waits for it, bounded by the same `HANDOVER_WAIT`: `bringUp` reads `closed` as soon as it has a process and stops it there, so the wait ends with the old host already on its way out. `nested-proxy.test.ts`'s `a restart waits for a host inside that is still starting, and stops it` is the case, and it failed first on `expected true to be false` - the close had already resolved by the time the process was handed over.
