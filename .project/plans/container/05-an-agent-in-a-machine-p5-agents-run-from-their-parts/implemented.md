Claude, each shipped ACP preset, and the nested `ahpd` that cofold and pi run in come from their parts, so a machine made from any glibc image runs them with nothing of this host's binaries mounted.
Each keeps its configuration in a state volume per provider, seeded from a few host files and never a login file; a profile with `state: "host"` mounts this host's configuration as before.
`computerCli: "host"` mounts the host's `claude` instead of the part, and `computerCliFallback: "host"` does so only when the part cannot be built.
A Claude variant's CLI in a machine gets its own `env` and nothing of the daemon's, and a value the vault fills for a need reaches only the agent whose need declared it.

## Departures from the plan

- Task 04: each Claude variant keeps its state at its own `computerConfigDir`, `/ahpd/<provider>` by default, so each provider has its own state volume, rather than every variant sharing `/ahpd/claude`; this follows container/05 p6, Softov, 2026-10-05: "One per provider".
- Task 09: a `$secret` in a Claude variant's `env` is read when the plugin loads, as the preset `env` already was, not at session start; a preset whose secret cannot be read is skipped with a line naming it, so only that item fails.
- The review's decision 1 needed a version for one package of a part apart from the part's own, so the versions file takes `<package>@<version>` in `packages`, and the tag carries it.
- The dev container relay has no agent, so it is given every agent's vault-filled values, as before.
- pi's docs say a variable named only in pi's own `models.json` does not reach a machine: a profile's `needs` fill only declared needs, so the plan's "a profile adds it as a need" has no field to do it with today.
