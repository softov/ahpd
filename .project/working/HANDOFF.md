## Constraints worth knowing before touching any of that

- **The gate has two boundaries, and they are not one.** A *command* is checked in `handle` against `NEEDS`/`capabilityFor`; a *dispatched action* is checked at the top of `applyDispatch` against `dispatchNeeds`, keyed by the channel and refusing with `rejectionReason`, because a notification carries no id to put a `-32007` in. A notification that acts is a new hole unless it is added to the second one.
- **A computer is a resource a person manages, and a session can run in one.** `computer://<id>` is the name, `resourceWrite` with a JSON manifest (`image`, limits, `mounts`, `workdir`) makes one and `resourceDelete` destroys it, gated as `computer:read`/`computer:write` through `capabilityFor`. A session names one with the plugin-contributed `computer` setting, which reaches the backend in `Start.settings`; a backend asks `Start.computers.how(id, ...)` for a spawn descriptor and must refuse rather than run on the host when it cannot reach the machine. That refusal is built for all three backends: `machineAsked(start)` reads the setting (an empty value is the host, not a machine named `''`) and `refuseComputer(start, 'Claude Code')` throws when there is no `computers` port, which is the first thing both non-ACP `create`s do. The three model tools declare `advancedPermission` and are withheld unless the daemon sets `advancedTools`, and the reference twelve declare nothing.
- **A grant is a subject and a verb.** `file:write` is what must stay open or VS Code cannot save; `computer:write` is named or not had, and `file:write` confers no scheme. `*` stands in either position and `admin` is `*:*`, which is the only thing that reaches every scheme. `NEEDS`, `dispatchNeeds` and `capabilityFor` in `host.ts` are the three places a method's pair lives, and the staleness test holds the first of them. `guest` is what `user add` defaults to and it looks without touching.
- **`defaultShell` is the connection's**, in `Connection.config` under `PER_CONNECTION`; `rootState` drops those keys from the host's half and overlays the connection's own. `createTerminal` uses the asking connection's; a `!command` and the backend factory open no shell from a person at all.
- **The door is a door, and the deployment token is the host.** A socket admitted on `connectionToken` is root: every capability including a scheme no role names, and `authenticate` can neither replace nor revoke it. It is a flag on the connection and not a principal, because a person signing in must not demote the operator. Any other token opens the door and names nobody, so `authenticate` is what authorizes; `trustToken` in the configuration (or `--trust-token`) trusts everybody's token as their authorization, and a record's own `trustToken` decides for one person and wins over the host. It is off by default, and that is decision `the-door-is-a-door`.
- **A role is read on every command.** `Users.verify` hands out a principal that answers `standing()` and `can()` by reading the file again, so removal refuses the next command with `-32007` and a changed role with `-32009`. A principal built by hand carries no `standing` and is treated as still standing, which is what keeps the tests and an embedder working.
- **The advertised record names an issuer only when one is configured.** `authorization_servers` is absent rather than wrong otherwise, because this host is not an RFC 8414 issuer and a documentation URL there can match a client's provider for the wrong origin. `resource` is an https identifier derived from the listen address or named by `--resource`.
- **An issuer answers for a subject, and the directory answers for roles.** `fileUsers.verify` compares a local hash first and asks an issuer only when nothing matched, matching the subject against a record's `id`. The host's `issuer` is the default; a record's own `issuer` wins, and the advertised record lists every provider with the union of their scopes. A record's `rolesFrom` names a claim whose values are roles this file defines, and the whole answer travels with `who` so one sign-in is one question; the claim's grants are stamped at sign-in and the record's roles stay live. A token is offered to the default first and then to each issuer a record names, so a host with several issuers shows a token to more than one of them. An unreachable issuer and a refused token both answer `-32007`, so the two are indistinguishable on purpose. The door is local secrets only: `verify` is reached before the socket exists and no issuer is asked there, which is why a record with no minted secret is a protocol credential and not a connection token. An issuer URL, and the `userinfo` endpoint it names, may be https anywhere or plain http on loopback only - `isIssuerUrl` in the SDK is the one test, used by `namedIssuer` and by `oidcIssuer`, and `issuerKind`/`issuerFrom` are the one rule that turns a name into a provider for both the configuration and the file.
- **The root `configChanged` echo cannot be split per connection.** `test/conformance.test.ts` pins exactly one echo per dispatch, and `serverSeq` and the replay buffer are one per host, so a per-connection action would be replayed to whoever reconnects next.
- **An unconfigured daemon is inert.** No `users` file means no principal anywhere and nothing refused; every existing suite is the proof, so a change that makes an unconfigured host stricter is a change to the contract.
- **The review's lesson.** A handler or a notification added later is unprotected until somebody remembers it. The staleness test asserts every handler is classified; the dispatch gate and the `PER_CONNECTION` split have no such guard.

## Environment notes that still cost time

- **pnpm's store is pinned read-only by `PNPM_HOME`.** `pnpm install`, `pnpm build` and `pnpm test` fail with `unable to open database file` under the default sandbox. The escape is `unset PNPM_HOME; export HOME=/github/.home CI=true`, then drive the tools directly: `node node_modules/vitest/vitest.mjs run`.
- **Do not add a `.npmrc` with `store-dir` inside the repo.** `cofold/.npmrc` is tracked (`engine-strict=true`) and was overwritten by one attempt; it is restored.
- **The job supervisor SIGTERMs long background commands.** One suite run is about 20 seconds and three sequential runs are fine; a five-run loop was killed. Keep one verification per background job.
- **CI runs `pnpm test` before `pnpm build`, so the suite must pass with no `packages/*/dist`.** A test that lists a workspace package by its directory reads `missing` in CI and `ready`/`unconfigured` in a built checkout. Rehearse by moving the builds aside, and restore each to its own package directory - moving one into `packages/<pkg>` puts the tree inside it.
- **A manifest change needs `pnpm install --no-frozen-lockfile` once**, because `CI=true` implies a frozen lockfile. `pnpm-lock.yaml` carries one importer per package.
- **npm cannot stage a name that has never been published**; the failure is a bare `E401` that reads like a bad token. A new name needs one token publish, then `npm trust github <pkg> --file release.yml --repo softov/ahpd --allow-stage-publish --allow-publish -y`, which needs 2FA. An already-staged version answers `E409 Cannot stage previously published version`.
- **A tag can be moved while its release is only staged**, because nothing is installable until approval; force-pushing re-runs the Release workflow, which the resumable staging loop makes safe.
- **`pnpm build` did not build `packages/computer`.** Its `ahpd.entry` is `./dist/index.js`, so a daemon that loads `@ahpd/computer` by name got whatever `dist` happened to be there - on 2026-09-24 that was a build from before the write half existed, and the plugin advertised a read-only scheme while the daemon advertised it faithfully. The build script now names `packages/computer`, and a plugin whose entry is `dist` must be rebuilt after its source moves or the daemon reloaded afterwards.

- **`test/fixtures/wire.jsonl` is rewritten by `test/wire.test.ts`** with paths from the running environment. Restore it after a full run: `git show HEAD:test/fixtures/wire.jsonl > test/fixtures/wire.jsonl`.
- **`npm` needs `HOME` writable for its cache.** `/github/.npmcache` exists for that, and npm 12 for `npm stage`/`npm trust` is at `/github/.home/npm12`.

## The eight recent things worth reading in full

`plugin/10` and `plugin/11` were built on 2026-09-23, and they finish the computer. A machine is an object a person manages: a resource write creates it, a resource delete destroys it, and `computer:write` is the grant, which the host already derives from the scheme. A session names one through a plugin-contributed setting, and the ACP backend's one spawned command runs inside it through a `computers` port, so no backend has to import the computer package. The three model tools survive as a nested extra and are off until `advancedTools`, which is the correction to the blanket gate that was first written down and withdrawn. The decisions are `the-computer-is-an-object-a-person-manages` (which supersedes `a-machine-is-made-by-a-host-tool`), `a-tool-says-when-it-needs-advanced-permission`, `a-plugin-may-contribute-a-session-key` and `a-backend-reaches-a-computer-through-a-port`; the reading is [`research/a-computer-three-things.md`](../research/a-computer-three-things.md), and `.project/plans/plugin/10-.../implemented.md` and `11-.../implemented.md` have what was verified by hand.

`host/15` was built on 2026-09-23. The two issuer items that were actionable are done: `ahpd user add --issuer` sets a record's provider from the command line, and a record's `rolesFrom` names a claim whose values are roles this file defines, added to the record's own. The claim is read at sign-in and the record's roles on every command, which is two clocks on one principal and is decision `a-claim-names-the-roles-this-host-defines`. Verifying a JWT locally is all that remains of the issuer work.

`host/14` was built on 2026-09-23. A record may name its own `issuer` with the same names the configuration takes, the configuration's `issuer` is the default for the records that name none, and the record a client is told lists every provider the file uses with the union of their scopes. So two people on one host can sign in through two providers, which is what made the dev issuer usable for testing beside `github`. The decision is `a-record-may-name-its-own-issuer`; `FileUserOptions.issuer` changed from an `Issuer` to a name, and `issuerFor` is the resolver a test injects.

`host/13` was built on 2026-09-23, and it reverses the half of `host/09` that made a personal connection token arrive as its owner. The door now admits a socket and names nobody, `authenticate` is what authorizes, and the deployment's token is still root. `trustToken` - a host key or a record's own field, off by default - is the opt-out for a client that can only carry a URL. The decision is `the-door-is-a-door`, which supersedes `the-door-token-is-the-host` on that sentence only; the two layers `docs/USERS.md` describes were nominal for a personal token before this, and are true now.

`host/12` refined `host/08` so a local issuer may be plain http. A deployment can name `github` or an OpenID Connect issuer, the record carries it in `authorization_servers`, and the issuer answers who a token belongs to while the user file still answers what they may do. The local hash is checked first, so a deployment that mints secrets is unaffected and never depends on an issuer being reachable. Its decisions are `an-issuer-answers-for-a-subject` and `an-issuer-may-be-plain-http-on-loopback`; the protocol gap it works around - a host-wide login has no home in AHP, so it rides on every agent - is in `.project/research/a-host-level-protected-resource.md`.

`host/07` was built on 2026-09-23. The advertised sign-in record stopped naming
a documentation page as an authorization server, which could match a client's
GitHub provider and send somebody to sign in to the wrong issuer, and a person's
own connection token stopped being the only thing a socket could say. Its
decisions are `a-host-advertises-only-what-is-true` and
`a-connection-token-may-carry-a-person`; the second is superseded twice over now -
by `the-door-token-is-the-host` on who the door key is, and by
`the-door-is-a-door` on whether a personal token carries a person at all - and
`authenticate` is what survived both.
