# What is left

Open scopes only. A row comes out when the work lands, and git keeps what was here before.

## Agents as extensions

The port is already there: `createHost` takes a list, `packages/sdk/src/types/agent.ts` imports no runtime value, and `@ahpd/agent-claude` is a package the host knows nothing about. What is missing is that the daemon hardcodes the list, so a second backend is a rebuild rather than an install. These five are in the order they should land, and each one is worth doing on its own.

| | |
| --- | --- |
| load agents from configuration | `packages/server/src/main.ts` names `claude({ paths })` in the literal, so nothing else can be added without editing it. An `agents` key in `config.json` holds npm specs, resolved with `createRequire` against `~/.config/ahpd/package.json` so installing a backend is `npm i` in the config directory and `@ahpd/server` never grows a dependency on one. A package that throws on load is reported and skipped rather than taking the daemon down with it, and a duplicate `provider` refuses at startup: it is the routing key a client names in `createSession`, so a collision is a turn delivered to the wrong backend with nothing on screen to say so |
| `@ahpd/agent-acp` | One bridge, several backends. `copilot --acp`, `codex-acp` and `gemini --experimental-acp` are the same seven methods and eight `session/update` variants, so the package is loaded once per backend with `provider` as the only thing that differs. `session/update` carries `agent_message_chunk`, `agent_thought_chunk`, `tool_call` and `tool_call_update`, which are `chat/delta`, `chat/reasoning` and the tool actions; `session/request_permission` is `confirm`. Capabilities come from the `initialize` reply and not from the typings - Copilot 1.0.80 answers `sessionCapabilities: { close, list }`, which `@zed-industries/agent-client-protocol@0.4.5` does not name - so which `Agent` members this build offers is decided at handshake |
| ports through `Start` | An ACP agent asks the client for `fs/read_text_file`, `fs/write_text_file` and `terminal/create`, and `Start` carries `tools` but neither `resources` nor `terminals`. So a bridge builds its own file and shell access beside the ones the host already holds, and outside the `within()` check that is the only answer to whether a path may be reached. The backend below wants the same thing, which is what makes this worth changing rather than working around twice |
| `@ahpd/agent-openai` | OpenRouter, Ollama, llama.cpp, LM Studio and vLLM are one `/chat/completions` behind a `baseUrl` and a key, so they are profiles of one package rather than four. It is the only backend with no harness behind it, so the package supplies the three things the others arrive carrying: the loop that turns tool calls into results and back, the tools themselves with the confirmation policy around them, and a transcript store on disk, because `list()` and `transcript()` otherwise have nothing to read. A model that cannot call tools degrades to a chat backend rather than offering tools that never fire |
| native codex, if fork and rewind earn it | `codex app-server` is 82 client methods to ACP's seven, and four of them are optional members of `Agent` that the ACP path leaves empty: `thread/fork` for `Start.forkAt`, `thread/rollback` for `rewindAt` and `chat/truncated`, `turn/steer` for `Session.steer`, and `thread/list` with `thread/read` for the catalogue. It also takes host tools directly, through the `item/tool/call` server request, where ACP takes them only as an MCP server. The bindings are generated rather than written - `codex app-server generate-ts` - but the protocol is marked experimental, so the codex version wants pinning. Both paths are the same `Agent`, so choosing between them stays a config edit |

## Copilot goes through the CLI

VS Code does not: it exchanges a GitHub token at `api.github.com/copilot_internal/v2/token` and posts to `api.individual.githubcopilot.com/chat/completions`, or the `business` or `enterprise` host named by the plan in the token response, with `Copilot-Integration-Id` and `X-Initiator` headers on it. The shipped `@github/copilot` bundle does the same thing. It is OpenAI-shaped, so it would be an auth provider inside `@ahpd/agent-openai` rather than a backend of its own, and `Agent.protectedResources` with `Start.credentials` is already the seam the token belongs in.

The integration id is the reason not to. It is allowlisted to editor integrations, sending one that was issued to somebody else is outside Copilot's acceptable use, and what that costs is the account rather than a `403`. `copilot --acp` is GitHub's own programmatic surface and gives the whole agent, tools and approvals and sessions included. GitHub Models at `models.github.ai/inference` is the documented way to reach a raw model with a personal access token, on its own quota rather than a Copilot subscription, and drops into the OpenAI backend unchanged. Asking GitHub for an integration id is the third answer, and the only one that makes the direct path a real option.

## Telling somebody the version is old

`https://registry.npmjs.org/-/package/@ahpd/server/dist-tags` answers `{"latest":"0.3.0"}` in 18 bytes, and that is the whole check. The alternatives are worth naming so nobody reaches for one later: `/latest` is 2,252 bytes, the abbreviated packument 1,826 and the full one 20,226, and every one of them answers more than was asked.

Read the answer out of a file and refresh in the background, six hours apart. A notice that arrives one run late is still a notice, and a start that waits on a registry is a start that hangs on a network nobody can see. Only the daemon asks, because it is the process that was going to be long-lived anyway: `fetch` holds the event loop open, and a request still in flight is what leaves `ahpd status` sitting there after it has printed. So the daemon writes `update.json` beside `daemon.json` and `sessions.json`, and the `start` line and `ahpd status` read it and say what it said without touching the network - which is how the automations note already reaches a person.

Every failure is the same answer. Offline, a proxy that blackholes, and a `404` because this package is not on npm yet are all nothing to report rather than a word on somebody's screen. The comparison is written rather than acquired, because neither repository has `semver` and this does not earn one: a prerelease loses to its own release, and a local build ahead of npm reports nothing at all. Both of these run ahead of the registry most days, and a tool that says so every start is a tool people switch off.

Off with `--no-update-check`, `NO_UPDATE_NOTIFIER`, `CI`, or `updateCheck: false` in the configuration. The daemon has no terminal, so the configuration key is the one that matters here. `npm_config_registry` is read before npmjs.org is assumed, so somebody behind a mirror is not quietly reaching past it.

`ahpc` gets the same against `@softov/ahpc`, which makes these the second instance of the duplication below.

## Deliberate duplication

`resourceWrite` is symmetrical, so `ahpd` and `ahpc` each implement the whole of it: the same flags, the same order of preconditions, the same append and insert arithmetic. `ahpc` does not depend on `@ahpd/sdk` and is not going to. Both copies carry a comment naming the other.

What now checks that they still agree is `test/fixtures/resource-write.json`, checked into both repositories byte for byte, with a runner in each - `test/resource-write.test.ts` on both sides - so twenty-one cases run against both implementations and a divergence fails a build rather than waiting for somebody to read the two files side by side. What running it here cannot catch is a case added on one side and never copied to the other, because there is no shared package to hold the file; each repository's CI reads the other's copy over HTTP and diffs it, which is what closes that.
